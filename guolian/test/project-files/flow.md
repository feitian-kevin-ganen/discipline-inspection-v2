# 审批流程说明（flow.md）

> 本文档总结系统当前唯一的审批场景——**学习资料（资料管理）审核**。
> 系统未使用任何工作流引擎（无 Flowable/Activiti/Camunda），审批为业务代码内硬编码的单级状态机。

## 一、场景概述

| 项 | 内容 |
| --- | --- |
| 审批场景 | 学习资料发布前审核（ LIB-10 ） |
| 流程引擎 | 无，状态字段 `t_learn_material.audit_status` 驱动 |
| 涉及模块 | exam-learn（后端）、exam-admin-web（管理端） |
| 配置开关 | `lib.auditRequired`（系统参数，默认 **开启**）；关闭后全部免审直接发布 |
| 审批级数 | 单级，一级审批即终结 |
| 审批留痕 | 仅记录 `audit_by` / `audit_time` + 一条系统日志（t_sys_log）；**驳回意见不落库**（详情接口 auditComment 恒为 null） |

## 二、流程发起人

| 项 | 内容 |
| --- | --- |
| 发起人角色 | 各级机构管理员（二级管理员 L2_ADMIN / 子管理员 SUB_ADMIN 等，具备"资料管理"菜单权限者）；**超级管理员、总部管理员也属于发起人，但可走免审通道** |
| 发起内容 | 学习资料：视频（mp4）、文档（pdf/doc/docx/ppt/pptx）、图文（外链解析或富文本录入），含标题、摘要、标签、分类、学习时长、可见范围、封面等 |
| 发起入口 | 管理端 → 资料管理 → 新增资料 / 编辑资料（`POST/PUT /api/v1/lib/materials`） |
| 发起时记录 | 上传人 `create_by`、上传单位 `upload_org_id` / `upload_org_path`（后续审核人权限判定依据） |

## 三、审批人

| 项 | 内容 |
| --- | --- |
| 审批人角色 | ① **超级管理员（SUPER_ADMIN）/ 总部管理员（HQ_ADMIN）**：可审全部，直通；② **上传单位的上级管理员**：按机构树判定，本人 `orgPath` 是上传单位 `uploadOrgPath` 的真前缀（`startsWith 且不等`） |
| 审批动作 | 通过（APPROVE）/ 驳回（REJECT，审核意见必填） |
| 审批入口 | 管理端 → 资料管理 → 待审核列表 → 审核（`POST /api/v1/lib/materials/{id}/audit`） |

## 四、流程节点

### 状态机

```
              创建/编辑(非超管·总管,开关开)                通过(APPROVE)
 ┌────────┐ ───────────────────────────────▶ ┌────────┐ ─────────────▶ ┌────────┐
 │ 0 草稿  │                                  │ 1 待审 │                │ 2 已发布│
 └────────┘                                  └────────┘                └───┬────┘
      ▲                                         │ 驳回(REJECT,意见必填)     │ 下架(OFFLINE)
      │                                         ▼                          ▼
      │      超管/总管可直接发布(跳过审核)      ┌────────┐                ┌────────┐
      └───────────────────────────────────────│ 4 已驳回│                │ 3 已下架│
        （开关开启时非超管/总管禁止此路径）      └────────┘                └───┬────┘
                                                                             │ 重新发布(PUBLISH)
                                                                             ▼
                                                                        回到 2 已发布
```

### 节点说明

| # | 节点 | 状态变化 | 说明 |
| --- | --- | --- | --- |
| 1 | 创建资料 | → 1 待审（默认路径） | 审核开关 `lib.auditRequired=on` 且发起人非超管/总部管理员：进入待审 |
| 1' | 创建资料（免审通道） | → 2 已发布 | 开关关闭，或发起人为超级管理员/总部管理员：免审直接发布（`need_audit=0`） |
| 2 | 编辑资料 | → 1 待审 | 开关开启时非超管/总管编辑（含换版 version+1）后**需重新审核**；超管/总管编辑不影响当前状态 |
| 3 | 审核（唯一审批节点） | 1 → 2 或 1 → 4 | 仅"待审"状态可审核；审批人限超管/总部管理员或上传单位的上级管理员；通过→已发布，驳回→已驳回（意见必填，仅写系统日志） |
| 4 | 发布 | 0/4 → 2；3 → 2 | 已下架可重新发布；**草稿/驳回直接发布仅超管/总管可用**（开关开启时其他人报"资料须先提交审核"）；重复发布幂等 |
| 5 | 下架 | 2 → 3 | 仅已发布可下架（`requireInScope` 限本单位数据范围内操作） |
| 6 | 结束 | 2 已发布 | 已发布即流程终点：考生端可见（`audit_status=2` 才下发），可继续学习；下架/重新发布属运营动作，不在审批链路内 |

> 说明：状态 `0 草稿` 在当前代码中仅为状态机预留（无任何代码路径会写入 0），创建后要么是 1 待审、要么是 2 已发布；不存在显式的"提交审核"动作，进入待审由创建/编辑自动触发。

## 五、关键规则汇总

| 规则 | 实现位置 |
| --- | --- |
| 初始状态判定 | `LearnMaterialService.applyInitialAuditStatus()` |
| 审核权限（超管/总部直通 + 上级管理员 orgPath 前缀判定） | `LearnMaterialService.audit()` |
| 通过后写 audit_by/audit_time + 系统日志 | `LearnMaterialService.audit()` |
| 编辑后重新审核 | `LearnMaterialService.update()` |
| 发布/下架状态校验 | `LearnMaterialService.publish()` |
| 考生端仅见已发布（audit_status=2） | `LearnAppService.pageVisible()` / `LearnMaterialService.requirePublished()` |
| 审核开关 | 系统参数 `lib.auditRequired`（SysConfigService） |

## 六、现状与局限

- 单级审批，无多级/会签/转办/加签/催办；
- 无流程实例与审批历史表，驳回意见不落库，无法追溯；
- 待审无消息通知（依赖管理端主动查看待审核列表）；
- 若未来需要多级审批或可配置流程，需引入工作流引擎，改造面集中在 exam-learn 的 audit 段与 `audit_status` 字段。
