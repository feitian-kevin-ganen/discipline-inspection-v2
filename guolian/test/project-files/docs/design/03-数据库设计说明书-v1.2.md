## 1. 引言

### 1.1 编写目的

本文档描述纪检监察人员在线考试系统的数据库逻辑结构与物理结构设计，包括表结构、字段定义、索引、约束、分区与归档策略、关键场景 SQL 示例、数据安全与备份方案、初始化数据等内容，作为后端开发（实体/Mapper/Repository）、数据库部署、数据迁移与运维的依据。

本文档与《用户需求书》（requirement/01-在线考试系统用户需求书.md）中的功能需求一一对应，覆盖：组织架构与人员（FR-ORG）、学习资料（FR-LIB）、在线学习与学习统计（FR-LEARN / FR-LSTAT）、题库（FR-QUES）、试卷与分数设计（FR-PAPER）、考试场次与下发（FR-EXAM）、在线考试（FR-TAKE）、判分与阅卷（FR-MARK）、考试统计分析（FR-STAT）、系统管理（FR-SYS）全部模块。

### 1.2 范围

- 数据库管理系统：PostgreSQL 16（单实例起步，支持读写分离扩展）。
- 数据库名建议：`exam_db`；业务 Schema：`public`（单 Schema，不拆分）。
- 文件存储（学习资料、题目图片、封面等）不入库，仅存 URL/对象 Key，由本地存储或 MinIO 承载。
- V1.1 起纳入微信平台对接的库表：`t_org_user` 增加微信身份绑定字段（`mp_openid`/`unionid`），新增微信推送记录表 `t_notify_wx_log`；与站内信通道 `t_sys_notice` 并存。短信/企业微信通道仍仅预留枚举，不建表。

### 1.4 字段类型规范

| 用途 | 类型 | 说明 |
| --- | --- | --- |
| 主键 | `BIGSERIAL` | 雪花 ID 由应用生成时改用 `BIGINT`，本设计统一 `BIGSERIAL` |
| 分值/成绩 | `NUMERIC(6,2)` | 最大 9999.99，支持半分（多选漏选半分等场景） |
| 百分比/正确率/完成率 | `NUMERIC(5,2)` | 存 0~100 的百分数 |
| 时长 | `INT`（秒）或 `INT`（分钟，字段名带 `_min`） | 学习时长、视频播放位置用秒 |
| 计数 | `INT` | 切屏次数、被引用次数等 |
| 枚举/状态 | `SMALLINT` | 取值在 COMMENT 中说明 |
| 时间 | `TIMESTAMPTZ` | 一律带时区，禁止 `TIMESTAMP WITHOUT TIME ZONE` |
| 富文本/长文本 | `TEXT` | 题干、解析、日志内容 |
| 半结构化数据 | `JSONB` | 选项、答案、抽题策略、可见范围、快照 |
| 短字符串 | `VARCHAR(n)` | 按业务最大长度上浮 50% 取值 |

### 1.5 通用字段约定

除纯日志表（t_sys_log、t_sys_login_log）外，所有业务表包含以下审计字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGSERIAL | 主键 |
| create_by | BIGINT | 创建人（t_org_user.id） |
| create_time | TIMESTAMPTZ DEFAULT now() | 创建时间 |
| update_by | BIGINT | 最后修改人 |
| update_time | TIMESTAMPTZ DEFAULT now() | 最后修改时间（应用层维护，或触发器维护） |

### 1.6 字符集与时区

- 字符集：`UTF8`（建库指定 `ENCODING 'UTF8'`），排序规则 `zh_CN.UTF-8` 或 `C`（按部署 OS 支持情况，题干按拼音排序非硬性需求，推荐 `C` + 应用层排序）。
- 时区：数据库 `timezone = 'Asia/Shanghai'`；应用与库之间统一使用 `TIMESTAMPTZ` 传值。
- 建库语句：

```sql
CREATE DATABASE exam_db
  WITH ENCODING 'UTF8'
       LC_COLLATE = 'C'
       LC_CTYPE = 'C'
       TEMPLATE = template0;
```

### 1.7 快照设计总原则（重要）

本系统存在大量"按当时状态留存"的需求（FR-ORG-03、FR-STAT-04、FR-PAPER-05），统一采用**快照冗余**策略：

1. **组织快照**：答卷、学习记录、考生名单等业务发生时，冗余写入 `org_id` + `org_path` + `org_name` 三个字段。人员调岗、组织合并/改名后，历史统计仍按"当时单位"口径汇总，同时 `org_path` 支持按任意层级下钻。
2. **试卷快照**：试卷被场次引用即封存；随机卷在考生开考时把"实际抽到的题目、顺序、分值"整体快照到 `t_answer_sheet.paper_snapshot`，保证一人一卷可还原、断线续考可恢复、题库后续修改不影响在考/历史试卷。
3. **等级快照**：成绩发布时把等级编码、等级名称及所用规则 ID 写入 `t_answer_sheet`，等级规则变更不影响历史成绩（FR-STAT-04）。

## 2. ER 概览

### 2.1 领域模型说明

- **组织域**：`t_org_unit` 自关联成树（parent_id + 物化路径 path + level）；`t_org_user` 挂在叶子或任意节点上；人员与角色多对多（`t_org_user_role` → `t_sys_role`）。
- **学习域**：资料分类树 `t_learn_category` → 资料 `t_learn_material`；学员对资料产生 `t_learn_record`（进度 + 有效时长 + 心跳锚点）；`t_learn_task` 下达后生成人员任务快照 `t_learn_task_user`。
- **题库域**：题库目录树 `t_ques_bank` → 题目 `t_ques_item`。
- **试卷域**：`t_paper`（固定/随机两种组卷方式）→ 固定卷明细 `t_paper_question`；等级规则 `t_grade_rule` + `t_grade_rule_item` 被试卷引用。
- **考试域**：`t_exam_session` 引用试卷（版本/快照）→ 考生名单快照 `t_exam_candidate` → 答卷 `t_answer_sheet` → 逐题明细 `t_answer_detail`；主观题产生 `t_mark_task`。
- **统计域**：实时 SQL 聚合为主，`t_stat_exam_unit` 按"场次 × 单位"预聚合快照，支撑大集团层级下钻。
- **练习域（V1.1 新增）**：`t_practice_record` 一题一行记录练习作答（含组织快照与来源法规快照），支撑"我的练习记录"与错题回顾，不进入正式考试统计口径。
- **系统域**：`t_sys_config`、`t_sys_role`、`t_sys_log`、`t_sys_login_log`、`t_sys_notice`；V1.1 新增 `t_notify_wx_log` 记录微信订阅消息推送留痕。

## 4. 逐表详细设计

### 4.1 组织与人员域

#### 4.1.1 t_org_unit（组织架构表，对应 OrgUnit）

组织树采用 `parent_id` + 物化路径 `path` + `level` 三件套：`parent_id` 维护树的直接父子关系与调整归属；`path`（形如 `/1/3/8/`，含首尾斜杠、由祖先 id 拼接）支撑"某节点及全部下级"的前缀查询（数据权限过滤、层级下钻汇总）；`level` 限定层级展示与深度校验（建议 ≤ 6 级，FR-ORG-01）。根节点 `parent_id` 为 NULL、`path = '/<id>/'`、`level = 1`。

| 字段名 | 类型 | 可空 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| id | BIGSERIAL | 否 | — | 主键 |
| parent_id | BIGINT | 是 | NULL | 上级单位 id，根节点为 NULL |
| unit_name | VARCHAR(128) | 否 | — | 单位名称 |
| unit_code | VARCHAR(64) | 否 | — | 单位编码，全局唯一 |
| unit_type | SMALLINT | 否 | — | 单位类型：1 总部 2 二级集团 3 子企业 4 部门 |
| path | VARCHAR(512) | 否 | — | 物化路径，如 /1/3/8/ |
| level | INT | 否 | — | 层级深度，根=1 |
| leader_name | VARCHAR(64) | 是 | NULL | 负责人 |
| contact_phone | VARCHAR(32) | 是 | NULL | 联系电话 |
| sort_no | INT | 否 | 0 | 同级排序号 |
| status | SMALLINT | 否 | 1 | 状态：1 启用 0 停用 |
| create_by / create_time / update_by / update_time | — | — | — | 通用审计字段 |
| deleted | SMALLINT | 否 | 0 | 逻辑删除 |

主键：id。约束：`uk_org_unit_code(unit_code)`（含已停用节点，编码不复用）；`CHECK (level >= 1 AND level <= 10)`。
索引：`idx_org_unit_parent(parent_id)`；`idx_org_unit_path(path varchar_pattern_ops)`（前缀查询 `path LIKE '/1/3/%'` 走索引）；`idx_org_unit_type(unit_type)`。

```sql
CREATE TABLE t_org_unit (
    id            BIGSERIAL    PRIMARY KEY,
    parent_id     BIGINT       NULL,
    unit_name     VARCHAR(128) NOT NULL,
    unit_code     VARCHAR(64)  NOT NULL,
    unit_type     SMALLINT     NOT NULL,
    path          VARCHAR(512) NOT NULL,
    level         INT          NOT NULL,
    leader_name   VARCHAR(64)  NULL,
    contact_phone VARCHAR(32)  NULL,
    sort_no       INT          NOT NULL DEFAULT 0,
    status        SMALLINT     NOT NULL DEFAULT 1,
    create_by     BIGINT       NULL,
    create_time   TIMESTAMPTZ  NOT NULL DEFAULT now(),
```

#### 4.3.2 t_ques_item（题目表，对应 QuesItem）

题目为核心资产表。选项与答案统一使用 JSONB，按题型约定结构：

- 单选/多选 `options`：`[{"key":"A","content":"..."},{"key":"B","content":"..."}]`；`answer`：`{"keys":["A"]}` / `{"keys":["A","C"]}`。
- 判断题：`options` 固定 `[{"key":"T","content":"正确"},{"key":"F","content":"错误"}]`，`answer`：`{"keys":["T"]}`。
- 填空题：`answer`：`{"blanks":[["答案1","同义词1a"],["答案2"]]}`，外层数组按空序，内层为可接受同义词；`blank_config`：`{"ignoreCase":true,"ignoreWidth":true,"unordered":false}`（忽略大小写/全半角/多空乱序，FR-MARK-01）。
- 简答题：`answer`：`{"reference":"参考答案","points":["评分要点1","评分要点2"]}`。

>
> ```json
> {"quesId": 123, "quesType": 1, "score": 5, "sortNo": 3,
>  "stem": "……", "analysis": "……",
>  "displayOptions": [{"key":"A","content":"……"},{"key":"B","content":"……"}],
>  "optionOrder": {"A":"C","B":"A","C":"D","D":"B"},
>  "answer": {"keys":["C"]}}
> ```
>

### 4.8 索引设计与性能、分区/归档策略

#### 4.8.1 索引设计要点

1. **物化路径前缀查询**：所有 `path`/`org_path` 字段建 `varchar_pattern_ops` B-tree 索引（`xxx varchar_pattern_ops`），使 `WHERE org_path LIKE '/1/3/%'` 走索引范围扫描。这是层级下钻与数据权限过滤的核心索引。**不要**对这些字段建普通 B-tree 之外再建重复索引；`LIKE '常量前缀%'` 在非 C 排序规则下必须依赖 `varchar_pattern_ops`。
2. **JSONB 查询**：选项/答案/快照不做检索，不建索引；需要按值过滤的 `tags`、`knowledge_tags`、`visible_scope` 建 `GIN (jsonb_path_ops)`（只支持 `@>` 包含查询，体积小、写入代价低；如需 `?`/`?|` 等键存在查询改用默认 `jsonb_ops`）。
3. **高并发写入路径**：答案保存走 `uk_detail_sheet_ques` 唯一索引 UPSERT；心跳走 `uk_learn_record_um`。这两条路径的索引必须保持精简，不在其上叠加宽索引。
4. **外键与常用过滤**：所有 `session_id`、`paper_id`、`sheet_id`、`user_id` 外键列均已建索引（见各表 DDL）。大规模部署中若写入压力成为瓶颈，可将外键约束降级为应用层校验（保留索引），本设计默认保留 FK 以保证数据质量。
5. **联合索引顺序**：等值列在前、范围列在后；如 `idx_ques_item_bank(bank_id, status, ques_type, difficulty)` 同时覆盖"按目录选题"与"抽题过滤"。

#### 4.8.2 大表分区建议（5000 人同场、5 万+答卷规模）

- **t_answer_detail（最大表，预估亿级）**：建议采用 PostgreSQL 16 声明式分区，二选一：
  - **方案 A·按创建时间月分区**（推荐）：`PARTITION BY RANGE (create_time)`，月分区 + 每月自动建分区（pg_partman 或运维脚本）。优点：归档=直接 `DETACH PARTITION` 历史月份；统计与判分按时间局部性好。
  - **方案 B·按场次哈希分区**：`PARTITION BY HASH (session_id)`，16~32 个分区。优点：单场考试的明细集中、判分/导出单场数据时分区裁剪极有效；缺点：时间归档不直观。
  - 注意：分区表主键/唯一键必须包含分区键，即 `PRIMARY KEY (id, create_time)`、`UNIQUE (sheet_id, ques_id, create_time)`（方案 A）；外键引用分区表时 PG16 支持，但性能需压测验证。示例如下：

```sql
-- 方案A演进示例（初始可按普通表上线，数据量上来后用 pg_cron+迁移脚本切换）
CREATE TABLE t_answer_detail_p (
    id          BIGSERIAL,
    sheet_id    BIGINT       NOT NULL,
    session_id  BIGINT       NOT NULL,
    -- ... 其余列同 4.5.4 ...
    create_time TIMESTAMPTZ  NOT NULL DEFAULT now(),
    PRIMARY KEY (id, create_time),
    UNIQUE (sheet_id, ques_id, create_time)
) PARTITION BY RANGE (create_time);

CREATE TABLE t_answer_detail_2026_09 PARTITION OF t_answer_detail_p
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
CREATE TABLE t_answer_detail_2026_10 PARTITION OF t_answer_detail_p
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE t_answer_detail_default PARTITION OF t_answer_detail_p DEFAULT;
```

- **t_answer_sheet / t_exam_candidate / t_mark_task**：千万级以内普通表 + 现有索引即可；超过两千万行后按 `session_id` 哈希分区演进。
- **t_sys_log / t_sys_login_log**：天然时间序列，直接月分区或按月分表归档（见 6.3）。

#### 4.8.3 5000 人同场考试专项考量

- 答案保存为纯 UPSERT 热点写：保持行窄（明细行不含题干）、`fillfactor=90` 减少 HOT 更新失败、批量提交（前端 10~15 秒聚合一次多题保存）。
- 答卷主表 `switch_count`、`answer_time` 等高频更新列与快照大字段 `paper_snapshot` 分离存储（TOAST 自动满足，无需人工拆表）。
- 统计查询禁止在考试进行中直接全表聚合 `t_answer_detail`；进行中的监控数据（已交卷人数等）只查 `t_answer_sheet`/`t_exam_candidate`。
- `ALTER TABLE t_answer_detail ALTER COLUMN user_answer SET STORAGE EXTERNAL;` 可按需调整 TOAST 策略，默认即可。

## 5. 关键场景 SQL 示例

### 5.1 按组织层级下钻汇总考试统计（FR-STAT-02）

场景：查看某单位 `:orgPath`（如 `/1/3/`）**直接下级**各单位在某场次 `:sessionId` 的应考/实考/平均分/及格率，支持逐层下钻与同级排名。

```sql
-- 直接下级单位汇总（实时口径）
SELECT ou.id                                   AS org_id,
       ou.unit_name                            AS org_name,
       COUNT(ec.id)                            AS should_count,
       COUNT(s.id) FILTER (WHERE s.submit_time IS NOT NULL)        AS actual_count,
       COUNT(ec.id) FILTER (WHERE ec.candidate_status = 2)         AS absent_count,
       ROUND(AVG(s.total_score), 2)            AS avg_score,
       MAX(s.total_score)                      AS max_score,
       MIN(s.total_score)                      AS min_score,
       ROUND(100.0 * COUNT(s.id) FILTER (WHERE s.total_score >= es.pass_score)
             / NULLIF(COUNT(s.id) FILTER (WHERE s.submit_time IS NOT NULL), 0), 2) AS pass_rate
FROM t_org_unit ou
JOIN t_org_unit parent
  ON parent.path = :orgPath AND ou.parent_id = parent.id AND ou.deleted = 0
CROSS JOIN t_exam_session es
LEFT JOIN t_exam_candidate ec
  ON ec.session_id = es.id AND ec.deleted = 0
 AND ec.org_path LIKE ou.path || '%'           -- 单位及其全部下级
LEFT JOIN t_answer_sheet s
  ON s.session_id = ec.session_id AND s.user_id = ec.user_id AND s.sheet_status = 1
WHERE es.id = :sessionId
GROUP BY ou.id, ou.unit_name, es.pass_score
ORDER BY avg_score DESC NULLS LAST;            -- 同级单位排名
```

若启用 `t_stat_exam_unit` 快照，同样条件改为查快照表（`org_level = 本级+1` 或直接 `parent_id` 关联），毫秒级返回。

### 5.2 分数段分布统计（FR-STAT-03）

默认口径 0-59 / 60-69 / 70-79 / 80-89 / 90-100（`t_sys_config` 键 `exam.scoreSegmentDefault` 可配置；配置变更时由应用层动态生成 CASE 分支，SQL 模板不变）：

```sql
SELECT CASE
         WHEN s.total_score <  60 THEN '0-59'
         WHEN s.total_score <  70 THEN '60-69'
         WHEN s.total_score <  80 THEN '70-79'
         WHEN s.total_score <  90 THEN '80-89'
         ELSE '90-100'
       END AS segment,
       COUNT(*) AS cnt,
       ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS ratio
FROM t_answer_sheet s
WHERE s.session_id = :sessionId
  AND s.sheet_status = 1
  AND s.submit_time IS NOT NULL
  AND s.org_path LIKE :orgPath || '%'          -- 可选：按单位筛选对比
GROUP BY segment
ORDER BY segment;
```

### 5.5 随机抽题 SQL 思路（FR-PAPER-02）

按策略 JSONB 中每条规则（题型 × 分类 × 难度 × 数量）分别抽题；`withChildren=true` 时用题库物化路径展开分类范围：

```sql
-- 单条规则抽题：题库分类/1/5/及下级、单选、难度中、抽8题
SELECT qi.id
FROM t_ques_item qi
JOIN t_ques_bank b ON b.id = qi.bank_id AND b.deleted = 0
WHERE qi.status = 2 AND qi.deleted = 0          -- 仅启用
  AND qi.ques_type = 1
  AND qi.difficulty = 2
  AND b.path LIKE '/1/5/%'
ORDER BY random()
LIMIT 8;
```

集合化版本（一次事务内按策略全量展开，避免 N 次往返）：

```sql
WITH rules AS (
  -- 策略JSONB展开：一条规则按难度明细拆为多行；bankIds由应用层预解析为path前缀数组随参数传入
  SELECT r.ord,
         (r.rule ->> 'quesType')::smallint        AS ques_type,
         (it ->> 'difficulty')::smallint           AS difficulty,
         (it ->> 'count')::int                     AS need_count
  FROM ( SELECT ord, rule
         FROM jsonb_array_elements(:strategy::jsonb -> 'rules') WITH ORDINALITY AS t(rule, ord)
       ) r,
       LATERAL jsonb_array_elements(r.rule -> 'items') it
)
-- 实际实现建议：应用层先把 bankIds 展开为 path 前缀数组再传入，SQL 按 (ques_type, difficulty, path前缀) 分组抽题：
SELECT qi.id, qi.ques_type, qi.difficulty
FROM (
  SELECT qi.*, row_number() OVER (PARTITION BY qi.ques_type, qi.difficulty ORDER BY random()) AS rn
  FROM t_ques_item qi
  JOIN t_ques_bank b ON b.id = qi.bank_id
  WHERE qi.status = 2 AND qi.deleted = 0
    AND b.path LIKE ANY (:bankPathPrefixes)      -- 如 {'/1/5/%','/1/6/%'}
) qi
JOIN rules r ON r.ques_type = qi.ques_type AND r.difficulty = qi.difficulty
WHERE qi.rn <= r.need_count;
```

抽题结果在考生开考时整体写入 `t_answer_sheet.paper_snapshot`（一人一卷），或开考务预生成（全考生同卷，`same_paper=1` 时首个考生生成后复用）。`ORDER BY random()` 在 5 万题量、按分类+题型+难度过滤后候选集通常 ≤ 数千行，性能可接受；候选集超大时可先 `TABLESAMPLE` 或按 id 随机偏移预筛。

### 5.6 成绩排名 SQL（V1.1，任务书（四）：分数降序、同分按用时升序）

用时取交卷时写入的 `duration_sec` 快照（见 4.5.3），避免依赖 `submit_time - start_time` 现场计算造成的口径漂移：

```sql
-- 本场个人成绩排名：分数降序，同分按用时升序；row_number 生成名次
SELECT s.user_id,
       s.user_name,
       s.org_name,
       u.user_group,                                   -- 1派驻组 2子企业纪委 3纪检委员 9其他
       s.total_score,
       s.duration_sec,
       s.grade_name,
       ROW_NUMBER() OVER (ORDER BY s.total_score DESC,
                                   s.duration_sec ASC NULLS LAST,
                                   s.submit_time ASC)  AS rank_no  -- 兜底：再同分同时按交卷先后
FROM t_answer_sheet s
JOIN t_org_user u ON u.id = s.user_id
WHERE s.session_id = :sessionId
  AND s.sheet_status = 1
  AND s.mark_status = 5                                 -- 已发布
ORDER BY rank_no;
```

- 走 `idx_sheet_rank(session_id, total_score DESC, duration_sec ASC)` 索引；5000 人单场排序毫秒级。
- 未交卷/缺考考生不进入排名（`mark_status=5` 过滤）；缺考名单另查 `t_exam_candidate.candidate_status=2`。
- 历史成绩趋势（个人历次考试）：`SELECT session_id, total_score, duration_sec, grade_name, create_time FROM t_answer_sheet WHERE user_id = :userId AND mark_status = 5 ORDER BY create_time;`（走 `idx_sheet_user`）。
- 成绩导出（Excel）：上述排名 SQL 结果集走异步导出通道（EasyExcel 流式写出，FR-STAT-07）。

### 5.7 单位平均分排名 SQL（V1.2，任务书正式稿：按所属单位统计平均分排名）

按考生所属单位（派驻纪检组、各子企业等）聚合本场已合成成绩的平均分并排名；单位集合与归属口径同 5.1（单位及全部下级，`org_path` 前缀匹配）：

```sql
-- 单位平均分排名：AVG(total_score) 降序 + RANK 并列排名；仅统计已合成成绩的答卷
SELECT ou.id                                  AS org_id,
       ou.unit_name                           AS org_name,
       COUNT(s.id)                            AS sheet_count,
       ROUND(AVG(s.total_score), 2)           AS avg_score,
       RANK() OVER (ORDER BY AVG(s.total_score) DESC NULLS LAST) AS rank_no
FROM t_org_unit ou
JOIN t_org_unit parent
  ON parent.path = :orgPath AND ou.parent_id = parent.id AND ou.deleted = 0
LEFT JOIN t_answer_sheet s
  ON s.session_id = :sessionId
 AND s.sheet_status = 1
 AND s.mark_status >= 4                        -- 仅已合成成绩的答卷（4 已合成 / 5 已发布），答题中/判分中不计入
 AND s.org_path LIKE ou.path || '%'
GROUP BY ou.id, ou.unit_name
ORDER BY rank_no;
```

- 与个人排名（5.6）口径差异：个人排名面向考生公开，要求成绩已发布（`mark_status = 5`）；单位排名面向管理端，放宽至已合成（`mark_status >= 4`）即可统计，便于成绩发布前预览。如需与个人排名完全同口径，将条件改为 `mark_status = 5` 即可，SQL 结构不变。
- 与既有 org-summary 接口（5.1）的数据口径关系：二者同为"单位及全部下级（`org_path` 前缀）"的单位级聚合，单位集合与人员归属口径完全一致；5.1 org-summary 提供应考/实考/缺考/及格率等全指标（其平均分基于已交卷答卷实时计算），本节仅在该口径基础上取平均分维度做跨单位排名——可直接对 5.1 结果集按 `avg_score` 排序得到同口径排名，也可按上式独立查询（额外过滤 `mark_status >= 4`，口径更严格）。启用 `t_stat_exam_unit` 快照（4.6.1）后，对快照表按 `session_id` 过滤、`ORDER BY avg_score DESC NULLS LAST` 即可得到同口径排名，毫秒级返回。
- 排名函数取 `RANK()`（同分并列、跳名次），符合单位评比惯例；如需连续名次改用 `ROW_NUMBER() OVER (ORDER BY AVG(s.total_score) DESC NULLS LAST, ou.id)`（风格同 5.6 个人排名）。未合成成绩的单位 `avg_score` 为 NULL，以 `NULLS LAST` 排末位。同分次序支持 FR-STAT-10 的可配置口径"及格率降序→参考率降序"：在 `RANK()`/`ORDER BY` 中追加 `pass_rate DESC, attend_rate DESC` 即可（默认关闭、并列同名次）。

- **时点恢复**：开启 WAL 归档（`archive_mode=on`）+ 每周一次 `pg_basebackup` 基础备份，支持 PITR；关键操作（统考下发、成绩批量发布）前由应用触发一次即时全量备份并记录到 `t_sys_log`。
- 备份文件异地/异机存放，恢复演练每季度一次。
